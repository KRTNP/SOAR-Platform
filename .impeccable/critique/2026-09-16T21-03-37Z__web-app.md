# Design Specificity Verdict

**Authored for this product, decisively.** The tells are structural: `connectorState()` returns three values, not a boolean, and the mobile bar renders a marker for exactly the two states that change what a tap means. `ModeBadge` is deliberately the loudest element in `badges.tsx` while every other badge is quiet-by-default. `TargetCheck` renders the connector's prose verbatim and refuses to compile it into a "Verified" badge — verified to match the comment; there is no string matching. The Rollback row names the mechanism and declines to invent a release timestamp the API never exposes.

Lapses back to category-interchangeable: the `/approvals` desktop table is an 8-column admin grid whose job the 4-fact landing panel already does better; `/search` and `/login` are generic.

# Emotional Journey

**Peak — arrival.** The landing page answers "what needs me?" above the fold, and when approvals are unreachable it says so in warn text rather than rendering a reassuring "nothing awaiting your decision".

**High-stakes moment — well reassured.** Mode, target, predicted effect, requested-because, case, requester, expiry countdown and rollback all on screen before confirm is reachable; the button reads "Execute now" vs "Run simulation". Better than Splunk SOAR's parameter list because it also states what would undo it.

**Moment after — well reassured, then fragile.** The receipt says "that is the recorded state, not an independent re-check" and offers Check target + Release now in the same place. But one Escape keystroke while the two-call sequence is in flight throws that receipt away — the exact failure the receipt was built to prevent.

**Valleys:** Settings, where every failure is the same six-word shrug. `/audit`, where the log silently ends at 100. The queue, where "3 cases new or updated" sends you hunting.

# What's Working

1. **Three-state connector honesty encoded in types, not copy.** The fix is a union type that cannot collapse; the mobile variant drops the badge for `dry_run` only — the safe default doesn't need a marker, the two dangerous states do.
2. **The receipt refuses to derive a verdict.** Verbatim connector prose plus the time obtained plus "connector's own words, not interpreted." Every competitor in the prior art either has no post-action verification or fakes one with a badge.
3. **Badge economy that survives a glance.** Expected outcomes are plain text; the pill is reserved for the four values that need catching.

# Priority Issues

**[P1] The Modal's escape hatch destroys the highest-value state.** Escape and backdrop call `onClose` unconditionally while the Cancel button is disabled during pending, so a stray keystroke mid-execute unmounts the dialog before the outcome lands and the operator never learns whether the firewall was written. The panel also has no `max-h`/`overflow-y`, so the tallest variant cannot be scrolled on a phone. → `/impeccable harden`

**[P1] The audit log presents a truncation as the whole record.** The API hardcodes a 100-row cap and takes no paging parameters; the footer reads "of Y records returned by the API". At exactly 100 the operator cannot tell a complete log from a clipped one — the identical defect round 3 fixed on the queue, left standing on the one surface whose job is completeness. → `/impeccable clarify`

**[P2] Settings throws away the API's reason.** All six actions throw; callers catch into "Could not create tenant. Try again." An adr/0024 RBAC denial and a database constraint are indistinguishable, while `cases/actions.ts` already has the `guard()` that preserves `problem.title`. → `/impeccable harden`

**[P2] Unbounded `getAction` fan-out on `/approvals`.** One round trip per approval across pending *and* the full decided history, each with an 8s timeout, inside a `force-dynamic` render. The landing page fixed exactly this. Root cause is contractual: the API already holds the joined `Action` in `ApprovalView` and discards it. → `/impeccable optimize`

**[P3] "New since last visit" is a number with nowhere to land.** The count renders; no row is marked. The product's genuine differentiator over Defender/Elastic becomes a memory tax. → `/impeccable clarify`

# Persona Red Flags

**Alex (power user):** approving 8 pending decisions costs 8 × (click Review → wait for preview → click Execute) with zero keyboard path; the audit filter is client-side only so there is no shareable filtered URL.

**Sam (screen reader + keyboard):** the mobile sidebar is six icons with `sr-only` labels — correct for SR, but a sighted keyboard user under 768px gets six unlabeled targets. `Modal` uses `aria-label` while rendering a visible heading with the same string. The dialog's async results (preview resolving, `TargetCheck` returning) are not in a live region, so a blind operator gets no announcement when the connector answers.

**Riley (stress tester):** Escape during execute destroys the receipt. `/audit` with 100+ records shows a plausible total that isn't one. A tenant whose FK blocks deletion returns "Could not delete. Try again." forever with no reason. Two tenants created in the same millisecond both render as the same truncated prefix.

**Nat, the solo lab operator:** the ingest line answers "did the pipeline see it?" without leaving for Wazuh. But after approving a block he alt-tabs to OPNsense anyway if he dismissed the dialog early; when the queue says "3 new" he re-reads every row; and when an allowlist add is refused by his own Keycloak role, the console tells him nothing.

# Minor Observations

- `sinceLabel` uses `Math.round`, so a 35-minute-old visit reports "1h ago" rather than the sub-hour branch it has.
- The reduced-motion block only disables `.animate-pulse`; `animate-spin` (7 call sites) and `animate-in fade-in` are unguarded.
- `Modal size="lg"` is `max-w-md` = 448px for a dialog carrying ~8 content blocks.
- `--font-sans` is declared in both `design-tokens.css` and by `next/font` at equal specificity — source order decides.
- `approval-card.tsx` falls back to "No action intent specified" where the table shows "—"; two vocabularies for the same unresolved `getAction`.

# Questions to Consider

1. The `/approvals` page and the landing "Waiting on you" panel do the same job with different compositions, and the panel wins on every axis. What if `/approvals` were only the decided history?
2. `POST /v1/actions/preview` returns prose and the UI honourably refuses to parse it. What if the contract returned `{already_in_effect: bool, message}` — would "no additional effect" earn a badge, or does the refusal to interpret remain the more valuable property?
3. What would it take for `TargetCheck` to run automatically once, 3 seconds after execute — or does auto-checking re-introduce the plausible-placeholder risk the manual button was built to avoid?
4. Every destructive path has ceremony; no path has undo except Release. If this operator is the only user and every action is audited, what is the argument against a 30-second undo window on status transitions and case close?
